# 视频报告 → 飞书 v0.2 轮询接口

更新：2026-09-12。该适配层复用现有视频审核任务，将最终 `report.json` 固化为飞书 `audit_response_schema_v0.2` 包络。前端采用“上传后轮询”，不应让一个 HTTP 请求等待整段视频处理完成。

机器结果是风险候选和核验缺口，不是违法认定、平台过审保证或自动投放许可。

## 1. 接口流程

1. `POST /api/jobs` 上传视频，HTTP 202 返回 `job_id` 及三个 URL。
2. 每次按轮询响应的 `retry_after_ms` 请求 `poll_url`。
3. `terminal=false` 时继续轮询；`terminal=true` 时停止。
4. `audit_response_ready=true` 时请求 `audit_response_url`，取得严格 v0.2 审核结果。
5. `status=failed` 时不写审核字段，显示任务失败并保留 `job_id` 排查。

`completed` 和 `needs_attention` 都是已产出报告的终态。`needs_attention` 表示识别或核验覆盖不足，不是接口失败；前端应展示并转人工复核。

## 2. 上传请求

```text
POST <VIDEO_MVP_URL>/api/jobs
Content-Type: multipart/form-data
```

主要表单字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `video` | 是 | MP4/MOV/M4V，默认上限由 `VIDEO_MVP_MAX_UPLOAD_MB` 控制 |
| `record_id` | 建议必填 | 飞书记录 ID；同一非空值重试返回同一任务 |
| `industry` | 否 | 接受飞书枚举 `美妆/游戏/保健食品/通用`，也接受视频服务行业枚举 |
| `product_category` | 否 | 产品或服务品类 |
| `platform` | 否 | 兼容旧前端的单个平台字符串 |
| `platforms_json` | 否 | 推荐；将飞书平台数组序列化，如 `["小红书","抖音"]` |
| `mode` | 否 | `标准/极速/深度`；MVP 实际统一按标准模式生成报告 |
| `urgency` | 否 | `普通/加急`；留痕但不改变本机队列优先级 |
| `supplement` | 否 | 补充背景，不作为已验证事实 |
| `transcript_file` / `transcript_text` | 否 | 可选转写补充；无字幕时仍会识别视频音轨 |
| `proof_files` | 否 | 最多 5 份 PDF/DOCX/TXT/MD/JSON |
| `activity_text` / `landing_page_text` | 否 | 活动条件和落地页文本一致性核验输入 |

示例：

```bash
curl -sS http://127.0.0.1:8511/api/jobs \
  -F 'video=@/absolute/path/ad.mp4;type=video/mp4' \
  -F 'record_id=rec_xxx' \
  -F 'industry=美妆' \
  -F 'product_category=护肤' \
  -F 'platforms_json=["小红书","抖音"]' \
  -F 'mode=标准' \
  -F 'urgency=普通'
```

接收响应：

```json
{
  "job_id": "32位任务ID",
  "request_id": "rec_xxx",
  "status": "queued",
  "deduplicated": false,
  "poll_url": "/api/jobs/<job_id>",
  "audit_response_url": "/api/jobs/<job_id>/audit-response",
  "report_url": "/api/jobs/<job_id>/report"
}
```

前端应以上传响应里的 URL 为准，不自行拼接。

## 3. 轮询响应

```json
{
  "job_id": "...",
  "request_id": "rec_xxx",
  "status": "processing",
  "message": "正在识别视频音轨",
  "terminal": false,
  "retry_after_ms": 1500,
  "audit_response_ready": false,
  "poll_url": "/api/jobs/...",
  "audit_response_url": "/api/jobs/.../audit-response",
  "report_url": "/api/jobs/.../report"
}
```

前端建议增加总超时（如 30 分钟），但总超时只表示前端停止等待，不应把后端任务标记为失败或自动重新上传。

## 4. v0.2 最终结果

`GET /api/jobs/<job_id>/audit-response` 成功时返回：

```json
{"code": 0, "msg": "ok", "data": {"request_id": "rec_xxx", "matched_rules": []}}
```

`data` 的完整结构由 [`audit_response_v0.2.schema.json`](../data/schemas/audit_response_v0.2.schema.json) 约束。适配器保证：

- 口播/OCR 规则风险进入 `matched_rules`；
- 必要展示项、证明材料/活动/落地页缺口、画面语义候选也进入 `matched_rules`；
- 平台条款候选进入 `审核_平台规则预检` 及六段式意见，但不伪装成现行法律违规命中；
- 所有规则适用状态为 `needs_fact_verification`；
- 识别覆盖不足时，即使无命中也不返回“无明显风险”。

任务完成后会保存 `audit_response.json`，并将其 SHA-256 记入 `manifest.json`，便于回溯飞书实际取得的版本。在结果尚未就绪时请求该地址返回 HTTP 409 和 `code=-1`。

## 5. 幂等与重试

- 同一非空 `record_id` 再次上传会返回原 `job_id` 和 `deduplicated=true`，不重复分析。
- 如果业务上确实要审核同一条飞书记录的新版视频，应使用包含物料版本的新请求 ID，例如 `record_id:video_version`。
- 轮询 GET 可安全重试；不要因为一次轮询超时就重复 POST 大文件。
