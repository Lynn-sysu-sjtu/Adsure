# 规则并行审核工作台操作说明手册 v0.1

## 一、任务目的

本轮采用“DeepSeek 先预审、人工复核 AI 结论”的方式。DeepSeek 已先给出赛道、问题映射、角色、链路、资产处置、争议池建议和理由；人工只需确认是否准确，并在有差异时修正。原始规则库和生产链路不修改。

每位审核人需要一次性判断自己负责规则的以下事项：

1. 规则原文是否与当前问题目录准确对应；
2. 规则是否确实适用于当前赛道、平台或商品类型；
3. 一条规则是否应同时映射多个问题；
4. 规则属于直接违规依据、辅助依据、例外条件，还是补资料核查项；
5. 规则应进入普通文案召回、事实核验、主动补资料、流程参考或准入核验中的哪条链路；
6. 规则最终应保留、调整、转入旁路，还是提交争议讨论。

本轮审核结果将用于形成后续实验性规则资产，并与原规则引擎、原 `jsonbase` 规则库进行 A/B 测试。原始规则库和生产链路暂不修改。

## 二、审核文件

审核工作台：

`reports/approved_issue_tree_v03/规则并行审核工作台_DeepSeek预审_中文问题名_v0.3.xlsx`

工作台包含以下 Sheet：

| Sheet | 用途 | 是否填写 |
|---|---|---|
| 操作说明 | 查看简要规则和注意事项 | 否 |
| 并行审核主表 | 查看全部 218 个 UID、风险分布和任务包分配 | 否 |
| 任务包A | 成员 A 的独立审核区 | 是 |
| 任务包B | 成员 B 的独立审核区 | 是 |
| 任务包C | 成员 C 的独立审核区 | 是 |
| 争议池 | 登记无法独立判断、需要集体讨论的规则 | 是 |
| 校验结果 | 查看任务唯一性、分工均衡性和资产保护状态 | 否 |

**唯一填写原则：**每位成员只编辑自己负责的任务包。蓝色列为 DeepSeek 预审建议，只读；黄色列为人工复核和差异修正区。

## 四、风险标签和工作量积分

同一个 UID 可能同时拥有多个风险标签。审核人必须在同一行中完成所有相关判断，不需要去其他 Sheet 重复审核。

| 风险标签 | 含义 | 审核重点 | 积分 |
|---|---|---|---:|
| 跨目录重叠 | 同一 UID 当前挂在多个问题下面 | 判断多重映射是否合理，明确保留和删除的问题 ID | 3 |
| 问题错配 | 规则原文可能不能支持当前问题 | 比较规则原文与问题定义，确定准确问题 | 1 |
| 主动补资料 | 可能依赖资质、备案、授权或事实证明 | 判断能否仅凭文案认定违规，以及需要核验什么资料 | 2 |
| 移出普通文案树 | 不适合进入普通文案直接召回 | 确定应转入哪一种旁路资产 | 2 |
| 中低置信度 | 模型对适用范围或问题归属不稳定 | 人工核对适用对象、行为结构、法律效果和问题归属 | 1 |

风险标签只说明“需要检查什么”，不代表规则一定有问题，也不直接决定最终结论。

## 五、开始审核前的准备

1. 打开自己的任务包 Sheet，不要复制或重新排序整张表。
2. 开启表头筛选，确认“建议任务包”与自己领取的任务一致。
3. 在“负责人”列填写姓名。
4. 每开始处理一条规则，将“审核状态”改为“审核中”。
5. 审核时始终以“规则原文”为首要依据；规则标题、模型理由和风险标签只能作为辅助信息。
6. 法律、行政法规和平台规则要分别判断，不要因为表达相近就视为同一效力层级的规则。

## 六、单条规则标准审核步骤

### 蓝色 AI 建议与 `legal_issue`

蓝色列已由 `deepseek-chat` 逐条生成，包括：建议赛道、保留/删除问题 ID、最终映射角色、最终审核链路、资产处置、是否提交争议池、置信度、判断理由和人工复核重点。蓝色列是预审底稿，不要直接改写。

`legal_issue` 是早期问题映射的**过渡状态**，只表示“规则已经与某个法律问题节点建立关系”，没有说明它能否直接支持违规结论。因此它可以出现在“当前映射角色”，但不得作为最终角色保留。本轮必须细分为：

| 最终角色 | 含义 |
|---|---|
| `direct` | 可直接支持个案疑似违规判断 |
| `supporting_basis` | 仅提供上位法、原则性或总括性支持 |
| `exception` | 豁免、例外或排除条件 |
| `proactive_check` | 需要补充核验事实、资质、证明或材料，不是新增违规结论 |

### 黄色人工复核字段

| 字段 | 填写规则 |
|---|---|
| 人工复核AI结论 | 每条必填：全部准确、部分准确、不准确、需讨论 |
| 负责人、审核状态 | 每条必填 |
| 正确适用赛道、保留/删除问题ID、最终映射角色、最终审核链路、资产处置 | 仅在对应 AI 建议不准确时填写修正值 |
| 人工结论、审核理由 | 部分准确、不准确或需讨论时填写，只写差异和原文依据 |
| 是否提交争议池 | AI 建议不准确或人工无法独立裁决时填写 |
| 二审状态、二审意见、审核日期 | 按原规则填写 |

### 第零步：先复核 AI 整组建议

1. 阅读 AI 建议、AI 判断理由和 AI 人工复核重点，再对照规则原文。
2. 全部准确：只选“全部准确”，其余人工修正列留空。
3. 部分准确：只填写有差异的字段。
4. 不准确：填写正确结论和修正理由。
5. 需讨论：将审核状态设为“待讨论”，并提交争议池。

后续汇总采用“人工修正优先；人工留空则继承 AI 建议”。

### 第一步：确认规则身份

依次阅读：

1. `规则UID`
2. `规则标题`
3. `来源类型`
4. `法规或平台规则`
5. `条款`
6. `规则原文`

检查：

- 标题是否忠实概括原文；
- 法规或平台规则名称与条款是否一致；
- 原文是否完整到足以判断规制对象和行为；
- 规则是禁止性规定、限制性规定、披露义务、程序要求，还是例外条款。

如果标题和原文冲突，以原文为准，并在“审核理由”中注明。

### 第二步：确认适用范围

判断规则适用于：

- 通用广告；
- 游戏；
- 美妆；
- 保健食品；
- 特定平台规则；
- 特定商品、主体、媒介或场景。

在“正确适用赛道”中选择：`通用`、`游戏`、`美妆`或`保健食品`。

判断原则：

- 广告法中的一般性义务通常属于“通用”；
- 明确限定化妆品、保健食品或游戏的规则归入对应赛道；
- 平台规则仍按它所规范的商品或业务赛道归类，同时保留平台来源；
- 如果规则针对项目三个赛道以外的行业，不要直接删除，先判断是否属于通用规则；确实无关时提交争议池。

### 第三步：确认问题归属

查看：

- `当前一级问题`
- `当前二级问题`
- `当前全部问题`
- `当前全部问题ID`

逐一比较当前问题与规则原文：

- 原文完整支持当前问题：保留；
- 原文不支持当前问题：删除该映射；
- 原文支持另一个现有问题：迁移到正确问题；
- 原文确实同时支持多个问题：保留多重映射，并说明每个映射的依据。

填写方式：

- `保留问题ID`：填写最终保留的完整问题 ID；多个 ID 每行一个。
- `删除问题ID`：填写本次需要解除映射的完整问题 ID；多个 ID 每行一个。
- 若需要迁移但不知道正确问题 ID，将结论设为“待讨论”，不要自造问题名称或 ID。

### 第四步：确认映射角色

在“最终映射角色”中选择：

| 角色 | 判断标准 |
|---|---|
| `direct` | 文案出现相应行为时，该规则可直接作为疑似违规依据 |
| `supporting_basis` | 仅提供上位法、原则性或总括性支持，不能单独生成违规结论 |
| `exception` | 规定豁免、例外或排除条件，用于判断是否不构成违规 |
| `proactive_check` | 指向需要额外核实的资质、事实、证明或材料，不是新增违规结论 |

如果同一规则在不同问题中承担不同角色，应在“审核理由”中逐项说明，并提交二审。

### 第五步：确认审核链路

在“最终审核链路”中选择：

| 审核链路 | 适用情形 |
|---|---|
| 普通文案召回 | 仅根据广告文案或素材内容即可初步判断 |
| `fact_check` | 必须核验事实真伪、资质、备案、检测报告或第三方证明 |
| `proactive_check` | 内容层暂未构成违规，但完整投放需要主动检查材料或条件 |
| `workflow_reference` | 属于发布前审核、投放流程、履约或平台操作要求 |
| `platform_access` | 属于行业准入、账户资质、类目准入或平台投放资格 |

特别注意：

- “没有看到证明材料”不等于“已经违法”；
- 需要第三方材料才能判断的，不应机械标记为 `direct`；
- `proactive_check` 不应塞入 `matched_rules` 作为违规命中；
- 一条规则可能保留法律问题映射，同时在处理流程上进入事实核验链路，必须在理由中写清楚。

### 第六步：确定资产处置

在“资产处置”中选择：

| 选项 | 使用场景 |
|---|---|
| 保留 | 当前赛道、问题、角色和链路均正确 |
| 调整映射 | 规则保留，但问题归属需要调整 |
| 转旁路资产 | 不进入普通文案召回，转入事实、流程或准入链路 |
| 不纳入候选资产 | 与三个赛道和通用广告审核均无关，且没有旁路价值 |
| 待讨论 | 现有信息不足，无法稳定判断 |

“不纳入候选资产”是高风险操作，应提交二审。它只影响后续候选资产，不代表删除 `jsonbase` 原始记录。

### 第七步：填写审核理由

审核理由不得只写“同意”“错误”“建议调整”。请使用以下结构：

```text
原文适用对象：
核心规制行为：
问题归属判断：
映射角色判断：
审核链路判断：
资产处置理由：
```

示例：

```text
原文适用对象：保健食品广告。
核心规制行为：禁止利用广告代言人作推荐、证明。
问题归属判断：保留“保健食品广告禁止代言推荐证明”，删除通用代言人资格映射。
映射角色判断：direct。
审核链路判断：普通文案召回；文案出现代言推荐即可初步判断。
资产处置理由：保留并调整问题映射。
```

### 第八步：完成状态和二审标记

- 判断明确：`审核状态 = 已完成`。
- 仍有争议：`审核状态 = 待讨论`，`是否提交争议池 = 是`。
- 涉及高风险处置：`二审状态 = 待二审`。
- 普通且判断明确：可选择`无需二审`。
- 填写审核日期。

## 七、不同风险组合的处理方法

### 只有“问题错配”

重点比较当前问题与规则原文，填写保留或调整后的问题 ID。若角色和链路没有问题，可直接完成。

### “跨目录重叠 + 问题错配”

先判断规则真正支持哪些问题，再分别填写保留问题 ID 和删除问题 ID。不要因为系统已经建立多个映射就默认全部保留。

### “主动补资料 + 问题错配”

先确定正确问题，再判断规则是否需要材料才能成立。问题归属正确不代表可以直接认定违规。

### “移出普通文案树 + 主动补资料”

重点判断转入 `fact_check`、`proactive_check`、`workflow_reference` 或 `platform_access`。通常不应重新放回普通文案直接召回。

### 含“中低置信度”

不要单独为了置信度再审核一次。按照完整八步流程处理，并额外核对“模型置信度”和“历史判断理由”中的不确定点。

## 八、争议池使用规则

出现以下任一情形，应提交争议池：

1. 一条规则可能支持两个以上三级问题，且无法明确主次；
2. 上位法与平台规则对适用范围的表达存在冲突；
3. 无法区分直接违规与补资料核验；
4. 规则标题、来源和原文互相矛盾；
5. 认为需要新增、删除或合并问题节点；
6. 准备选择“不纳入候选资产”；
7. 规则可能影响多个赛道，但工作台只能选择一个赛道；
8. 现有规则原文残缺，无法作出可靠判断。

操作方法：

1. 在任务包中将“是否提交争议池”设为“是”；
2. 将“审核状态”设为“待讨论”；
3. 在“审核理由”中说明已确定部分和未确定部分；
4. 在“争议池”新增一行，填写 UID、争议类型、争议说明和建议方案；
5. 项目负责人集中裁决，并填写最终问题 ID、审核链路和资产处置。

同一争议不要在三个任务包中重复登记。

## 九、二审和质量控制

以下规则必须 100% 二审：

- 选择“不纳入候选资产”；
- 跨目录重叠规则；
- `direct` 与 `fact_check` / `proactive_check` 难以区分；
- 拟新增、删除或合并问题节点；
- 原文、标题或来源互相冲突；
- 同一规则拟保留多个问题映射；
- 审核人提交争议池的规则。

其他规则建议抽检：

- 普通问题错配：抽检 20%；
- 只有中低置信度标签且判断明确：抽检 10%；
- 已完成重复合并的规则：无需在本轮重新逐条审核。

二审人应检查：

1. 结论是否以原文而非标题为依据；
2. 问题 ID 是否来自现有问题树；
3. 删除映射后是否仍保留至少一个合理归属；
4. 补资料规则是否被错误写成直接违规；
5. “不纳入候选资产”是否确实没有通用或旁路价值；
6. 审核理由是否足以让后续人员复现判断。

## 十、每日协作机制

建议每天安排一次 20 至 30 分钟集中讨论：

1. 各成员报告已完成数量和待讨论数量；
2. 仅讨论争议池，不逐条复述已完成规则；
3. 项目负责人当场确定可裁决事项；
4. 需要法务进一步判断的事项保留“待二审”；
5. 会议结束后由原审核人把裁决同步回自己的任务包。

为避免版本冲突：

- 使用同一份共享文件协作时，不要另存多个成员版本；
- 如果必须离线分发，成员只返回自己的任务包 Sheet，由项目负责人统一汇总；
- 不要改动表头、列顺序、规则 UID 或当前问题 ID；
- 不要新增自由格式的结论词，优先使用下拉选项。

## 十一、成员提交前自检

每位成员提交前检查：

- [ ] 自己任务包中的每个 UID 均有负责人；
- [ ] 已完成规则均填写审核状态；
- [ ] 已填写正确适用赛道；
- [ ] 跨目录规则均填写保留问题 ID 和删除问题 ID；
- [ ] 已选择最终映射角色；
- [ ] 已选择最终审核链路；
- [ ] 已选择资产处置；
- [ ] 审核理由包含原文适用对象和核心规制行为；
- [ ] 待讨论规则均已登记争议池；
- [ ] 高风险结论已标记待二审；
- [ ] 未修改规则 UID、规则原文、表头和其他成员 Sheet。

## 十二、项目负责人汇总检查

收齐结果后，项目负责人检查：

1. 三个任务包的 218 个 UID 是否全部覆盖；
2. 是否存在同一个 UID 被多人重复填写；
3. 是否存在“已完成”但关键字段为空；
4. 所有争议池记录是否已有裁决或明确的后续责任人；
5. 所有“不纳入候选资产”是否完成二审；
6. 所有跨目录规则是否完成二审；
7. 问题 ID 是否来自当前批准的问题树；
8. 最终赛道、映射角色和审核链路是否使用允许值；
9. 是否保留完整的审核人、审核日期和理由；
10. 是否仍保持原 `jsonbase` 和生产链路未修改。

## 十三、审核完成后的工程步骤

人工审核完成后，再由统一脚本执行，不由成员直接修改规则 JSON：

1. 汇总三个任务包和争议池的最终结论；
2. 校验问题 ID、赛道、角色和链路字段；
3. 生成新的候选问题树和规则映射资产；
4. 保留 UID 合并、映射删除、赛道调整和旁路迁移日志；
5. 使用原规则库运行 baseline A；
6. 使用审核后的候选资产运行实验组 B；
7. 比较规则召回率、误召回率、正确法条命中率、主动补资料准确率和最终意见类型准确率；
8. 指标确认改善且无明显回归后，再决定是否写回规则 JSON 或接入生产链路。

## 十四、禁止事项

- 不直接修改或删除 `jsonbase` 原始 JSON；
- 不直接修改生产规则引擎；
- 不用规则标题替代规则原文作判断；
- 不因模型标记为中低置信度就默认模型错误；
- 不因规则需要补资料就默认广告已经违规；
- 不把 `proactive_check` 塞入直接违规命中结果；
- 不自行创造问题 ID、映射角色或审核链路名称；
- 不在多个 Sheet 重复填写同一 UID 的不同结论；
- 不在没有二审的情况下最终移除候选规则资产。
