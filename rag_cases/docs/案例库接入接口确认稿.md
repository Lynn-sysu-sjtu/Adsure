# 案例库接入接口确认稿

> 版本：v1.0
> 日期：2026-07-18
> 对接范围：飞书状态机、法务工作台、规则引擎、广告处罚案例库
> 本文冻结飞书法务工作台的正式 RAG 契约：`POST /cases/retrieve` 与
> `GET /health`。`POST /search` 仅作为已有调用方的兼容路由保留。

## 0. 先确认三件事

### 0.1 `/audit`、`/search` 和 `/cases/retrieve` 的边界

- `POST /audit`：规则引擎审核接口。飞书状态机点击“开启 AI 审核”时调用，返回风险、审核意见、命中规则和 `routing`。
- `POST /cases/retrieve`：飞书法务工作台正式 RAG 接口；打开物料详情时调用，只召回公共案例。
- `POST /search`：已有多租户调用方的兼容接口，不作为本轮飞书联调契约。

案例库接口不负责决定 `routing`，规则引擎接口也不应把“相似案例”直接当作违法结论。

### 0.2 队友不会把飞书原始字段对象直接传给案例库

飞书侧会先把 `①运营·物料内容` 等中文字段转换成标准化 JSON。案例库只接收标准字段，不接收：

```json
{
  "fields": {
    "①运营·物料内容": "..."
  }
}
```

### 0.3 当前仓库已实现 HTTP 接口

当前代码已经具备：

- 从结构化案例构建 `case_summary` 和 `regulatory_logic` 两类切片；
- 使用自然语言 `vector_text` 生成案例摘要切片；
- 对切片执行字段加权 BM25，并可使用本地稠密向量做语义召回和 RRF 融合；
- FastAPI `POST /cases/retrieve`、`GET /health` 和兼容的 `POST /search`；
- `X-API-Key` 鉴权、公共/企业私有案例隔离；
- 生产/候选索引隔离、按 `case_id` 去重和完整案例回读；
- 输出带来源、审核状态和候选状态的检索结果。

当前代码尚不具备公网部署和长期运行环境。语义索引已经可以离线生成，但它是
仓库内 JSON 文件，不是外部向量数据库；部署机仍需安装
`requirements-semantic.txt` 中的依赖并准备指定模型。

因此下文 `/cases/retrieve` 是当前正式且可运行的实现。只有部署到双方可访问
的环境并安全注入 Key 后，才可表述为联调服务已上线。

## 1. 完整调用关系

### 1.1 AI 审核主链路

```text
运营点击“开启 AI 审核”
  → 飞书后端整理标准化 payload
  → POST /audit
  → 规则引擎执行规则召回与审核
  → 飞书回写 ②AI预审、③AI审核字段
  → 根据 routing 流转到运营或法务
```

### 1.2 相关案例展示链路

```text
用户打开物料详情
  → 法务工作台 GET /api/records/<record_id>/cases
  → 工作台从飞书记录取得 content、industry、platform
  → 工作台后端 POST /cases/retrieve
  → 案例库执行召回并返回 cases
  → 工作台展示“相关案例参考”卡片
```

前端不直连案例库。案例库 URL 和凭证只配置在工作台后端。

## 2. 飞书调用 `/audit` 时发送什么

### 2.1 标准请求体

```json
{
  "record_id": "rec_xxx",
  "mode": "标准",
  "industry": "美妆",
  "content": "15天见效，全网第一，焕发新生",
  "urgency": "普通",
  "supplement": "",
  "platform": ["小红书"],
  "material_type": "图文",
  "product_category": "护肤",
  "extras": {
    "产品备案名称": "某产品备案名称",
    "核心宣称功效": "提亮",
    "物料涉及场景": "信息流广告"
  }
}
```

### 2.2 字段约定

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `record_id` | string | 是 | 飞书记录 ID，用于回写和全链路排查 |
| `mode` | string | 是 | 当前使用 `标准`；后续可扩展 `极速`、`深度` |
| `industry` | string | 是 | `美妆`、`游戏`、`保健食品`或`通用` |
| `content` | string | 是 | 完整待审物料文本；空字符串应返回参数错误 |
| `urgency` | string | 是 | `普通`或`加急` |
| `supplement` | string | 是 | 补充背景；没有时传空字符串 |
| `platform` | string[] | 是 | 多选字段必须传数组 |
| `material_type` | string | 是 | 如`图文`、`短视频`、`Banner`、`直播话术` |
| `product_category` | string | 是 | 产品或服务类别 |
| `extras` | object | 是 | 行业专属信息；没有时传空对象 |

行业专属 `extras`：

- 美妆：`产品备案名称`、`核心宣称功效`、`物料涉及场景`；
- 保健食品：`产品备案名称`、`批准文号`、`核心宣称功效`、`物料涉及场景`；
- 游戏：`游戏名称`、`IP名称`、`物料涉及场景`。

### 2.3 `/audit` 调用约定

```text
POST <RULE_ENGINE_URL>/audit
Content-Type: application/json
X-API-Key: <通过安全渠道提供，不写入文档或仓库>
timeout: 10 秒
```

飞书侧当前约定：

- 超时不自动重试，由运营重新触发；
- `code != 0`、超时或网络异常时回退到“运营起草”；
- 不写入 ②、③ 段审核字段；
- 向运营展示红色失败卡片；
- 状态为“AI预审中”时拦截重复点击。

## 3. 法务工作台调用 `/cases/retrieve` 时发送什么

### 3.1 请求

```text
POST <CASE_ENGINE_URL>/cases/retrieve
Content-Type: application/json
X-API-Key: <通过安全渠道提供，不写入文档或仓库>
X-Request-ID: <可选，建议传飞书侧链路请求 ID>
timeout: 8 秒
```

```json
{
  "content": "待审物料文案全文",
  "industry": "美妆",
  "platform": ["抖音", "小红书"],
  "top_k": 3
}
```

### 3.2 请求字段

| 字段 | 类型 | 必填 | 接收规则 |
| --- | --- | --- | --- |
| `content` | string | 是 | 去除首尾空白后不能为空，最大长度由服务端配置 |
| `industry` | string | 是 | 首期接受`美妆`、`游戏`、`保健食品`、`通用` |
| `platform` | string[] | 否 | 缺省为 `[]`；必须是字符串数组 |
| `top_k` | integer | 否 | 默认 3，最小 1，最大 5 |

案例库不需要接收 `record_id` 才能检索。为便于链路追踪，后续可以增加可选 `request_id`，但不应将飞书记录 ID 写入案例正文或索引。

## 4. 我方如何触发案例召回

## 4.1 当前代码的真实召回机制

正式实现位于 `src/api.py`、`src/retrieval.py` 和 `src/semantic_index.py`：

1. 字段加权 BM25 对违法宣称、风险维度、规则 ID、产品和监管逻辑分别打分；
2. 本地多语种句向量对自然语言场景做余弦相似度召回；
3. `hybrid` 模式以 0.55 / 0.45 权重做 RRF 排序融合；
4. 结构化行业、产品、渠道、风险维度和规则 ID 过滤在打分前完成；
5. 语义索引缺失、与切片不一致或模型加载失败时，显式降级到词法检索。

三种模式由 `CASE_ENGINE_RETRIEVAL_MODE` 控制：`lexical`、`semantic` 或
`hybrid`。BM25 原始分、语义余弦和融合分分别使用不同的 `score_type`，不得
统一显示为“相似度百分比”。

## 4.2 当前索引选择行为

未显式指定切片文件时，当前测试代码会：

1. 查询含游戏、美妆、化妆品、保健品、普通食品、会销、概率等赛道词时，使用 `sector_candidate_chunks.json`；
2. 否则依次尝试 `candidate_chunks.json`、`production_chunks.json`、测试索引和样例索引。

这是开发期测试路由，不可直接用于生产接口，因为它会优先命中未核验候选案例。

## 4.3 `/cases/retrieve` 应采用的正式召回流程

接口适配层应按以下顺序执行：

1. 校验 `content`、`industry`、`platform`、`top_k`；
2. 生成自然语言查询：

   ```text
   行业：美妆。投放平台：抖音、小红书。广告内容：待审物料文案全文。
   ```

3. 按服务端环境配置选择索引：
   - 生产环境：只允许 `production_chunks.json`；
   - 隔离联调环境：可以显式使用候选索引，并在响应中标记 `candidate_data=true`；
   - 生产索引为空时返回空数组，不得自动回退候选索引。
4. 在打分前完成公开范围、来源核验、审核状态和行业兼容过滤；
5. 去除查询模板中的“广告、内容、平台、监管”等通用噪声词，避免跨行业误召回；
6. 按配置执行 BM25、语义向量或二者的 RRF 混合召回；
7. 语义召回低于阈值、BM25 不满足有效短语数或查询覆盖率的结果不进入对应候选集；
8. 同一 `case_id` 的 `case_summary` 和 `regulatory_logic` 命中结果去重，只保留最高分作为排序分；
9. 根据 `case_id` 回读完整结构化案例，补齐处理结果、法律依据、原始宣称和来源字段；
10. 将内部案例字段转换为接口字段并返回最多 `top_k` 个案例。

渠道元数据缺失时不作排除；已知且明确矛盾的渠道在排序前过滤。“互联网”这类
通用渠道仍与直播、微信、小红书等具体数字渠道兼容。
行业采用兼容分组：游戏请求只召回游戏案例，美妆请求只召回美妆、化妆品或
医美案例；保健食品请求可召回保健食品、健康产品及普通食品的功效宣传案例，
但响应始终保留案例原始 `industry`，不得混淆产品法律属性；通用请求不做行业
硬过滤。

## 5. `/cases/retrieve` 返回什么

### 5.1 成功响应

以下仅为字段结构示例，不代表真实案例：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "cases": [
      {
        "case_id": "case_xxx",
        "title": "案例标题",
        "content_snippet": "原案例广告宣称或与查询最相关的案例片段",
        "industry": "美妆",
        "platform": ["某投放渠道"],
        "violation_type": "违规类型",
        "risk_dimensions": ["风险维度"],
        "risk_level": null,
        "ruling": "处理结果摘要",
        "legal_basis": ["经来源核验的法律依据"],
        "regulatory_logic": "监管机关认定风险的逻辑摘要",
        "score": 0.991803,
        "score_type": "hybrid_rrf",
        "retrieval_method": "hybrid_rrf_v1",
        "similarity": 0.742925,
        "source_name": "公开来源名称",
        "source_url": "https://example.invalid/case",
        "raw_text_path": "data/raw_text/case_xxx.json",
        "review_status": "approved",
        "source_verification_status": "source_verified",
        "approved_for_rag": true,
        "candidate_data": false
      }
    ],
    "retrieval_meta": {
      "index_scope": "production",
      "index_version": "16位索引摘要",
      "top_k": 3,
      "returned": 1
    }
  }
}
```

### 5.2 返回字段来源和当前可用性

| 返回字段 | 内部来源 | 首期要求 | 说明 |
| --- | --- | --- | --- |
| `case_id` | 案例 `case_id` | 必返 | 案例唯一 ID |
| `title` | 案例 `title` | 必返 | 案例标题 |
| `content_snippet` | `illegal_claims`，无值时取相关切片 | 必返 | 最长 150 字；不得补写原文没有的宣称 |
| `industry` | `metadata.industry` | 必返 | 案例所属行业 |
| `platform` | `metadata.ad_channel` | 必返 | 有值时作为单元素数组返回；无值返回 `[]` |
| `violation_type` | 案例或 `metadata.violation_type` | 可空 | 不用 `risk_dimensions` 冒充 |
| `risk_dimensions` | 案例 `risk_dimensions` | 必返 | 数组 |
| `risk_level` | 当前案例库无稳定字段 | 可空 | 不得根据相似度推导高、中、低 |
| `ruling` | 完整案例 `penalty_result` | 可空 | 不得把 `regulatory_logic` 冒充裁决 |
| `legal_basis` | 完整案例 `legal_basis` | 必返数组 | 缺失时返回 `[]`，不得补写法条 |
| `mapped_rule_ids` | 案例规则映射 | 必返数组 | 只用于召回约束和规则关联 |
| `possible_liability_rule_ids` | 推定责任条款映射 | 必返数组 | 仅表示可能适用，待法律复核 |
| `legal_basis_details` | 法规目录与案例映射 | 必返数组 | 明确条、款、项、版本、来源、映射关系和复核状态 |
| `legal_basis_provenance` | 法律依据证据边界 | 可空 | 区分来源明确引用与适用性推定 |
| `regulatory_logic` | 完整案例 `regulatory_logic` | 可空 | 监管逻辑摘要 |
| `score` | 当前检索器排序分 | 必返 | 解释方式取决于 `score_type`，一律不是前端风险百分比 |
| `score_type` | 检索器 | 必返 | `bm25`、`semantic_cosine` 或 `hybrid_rrf` |
| `retrieval_method` | 检索器 | 必返 | `fielded_bm25_v2`、`dense_semantic_v1` 或 `hybrid_rrf_v1` |
| `match_evidence` | 检索器 | 必返 | 词法命中、查询覆盖率、语义余弦和融合分；未参与的信号为 `null` |
| `similarity` | 真实语义余弦 | 可空 | 该结果进入语义候选集时返回，否则为 `null` |
| `source_name` | 案例 `source_name` | 必返 | 来源名称 |
| `source_url` | 案例 `source_url` | 必返 | 生产案例必须为可回溯的 HTTP(S) URL |
| `raw_text_path` | 案例 `raw_text_path` | 必返 | 人工回溯路径 |
| `review_status` | 案例审核状态 | 必返 | 如 `approved`、`pending_review` |
| `source_verification_status` | 来源核验状态 | 必返 | 生产案例应为 `source_verified` |
| `approved_for_rag` | 案例审批状态 | 必返 | 生产结果必须为 `true` |
| `candidate_data` | 索引范围 | 必返 | 候选联调结果为 `true` |

### 5.3 为什么对队友原字段做了调整

- `risk_level`：当前案例库没有稳定的案例风险等级，不能编造。
- `similarity`：只返回真实语义向量余弦；纯词法命中为 `null`，不得把 BM25
  或 RRF 分数伪装成相似度。
- `legal_basis`：一个案例可能对应多条依据，使用数组比拼接字符串更安全。
- 具体法条不得覆盖来源原文；推定适用条款必须在 `legal_basis_details.relation`
  标记为 `applicable_rule_inferred`，并携带独立复核状态。
- 新增 `source_url`、`raw_text_path` 和审核状态：这是案例人工回溯和候选隔离的硬要求。
- 新增 `risk_dimensions`、`regulatory_logic`：便于法务理解召回原因，但不能替代规则引擎判断。

### 5.4 空结果

没有可用生产案例时：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "cases": [],
    "retrieval_meta": {
      "index_scope": "production",
      "index_version": "16位索引摘要",
      "top_k": 3,
      "returned": 0
    }
  }
}
```

法务工作台展示“暂无相关案例”，不影响 AI 审核和状态流转。

### 5.5 参数错误

```json
{
  "code": -1,
  "msg": "缺少必填字段：content",
  "data": null
}
```

建议错误类型：

- `content` 为空；
- `industry` 不在支持范围；
- `platform` 不是字符串数组；
- `top_k` 不是 1—5 的整数；
- API Key 无效或缺失。

HTTP 状态固定为：参数或 JSON 格式错误 `400`，鉴权失败 `401`，服务端未配置
Key 或索引/检索异常 `503`。索引或检索异常使用稳定响应：

```json
{
  "code": -1,
  "msg": "案例检索服务暂不可用",
  "data": {
    "cases": []
  }
}
```

调用方应记录该异常并降级展示空态，但不得将它统计为“正常无相关案例”。

## 6. `/audit` 返回什么给飞书

规则引擎成功响应保持队友已经接通的结构：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "resolved_mode": "标准",
    "mode_reason": "MVP阶段统一使用标准审核模式",
    "预审_风险等级": "高",
    "预审_命中要点": "命中要点文本",
    "预审_修改建议": "修改建议文本",
    "审核_审核意见": "完整审核意见",
    "审核_关键实体抽取": "关键实体文本",
    "审核_高风险词命中": "高风险词文本",
    "审核_平台规则预检": "平台规则预检结果",
    "审核_备案核查结果": "备案核查结果",
    "审核_推荐违规类型": ["绝对化用语", "虚假宣传"],
    "审核_推荐风险等级": "高",
    "routing": "法务",
    "matched_rules": [],
    "audit_time": 1784332800000
  }
}
```

字段约定：

| 字段 | 飞书处理 |
| --- | --- |
| `resolved_mode` | 写入③AI审核·审核模式 |
| `mode_reason` | 写入③AI审核·模式推荐理由 |
| `预审_风险等级` | 写入②AI预审·风险等级 |
| `预审_命中要点` | 写入②AI预审·命中要点 |
| `预审_修改建议` | 写入②AI预审·修改建议 |
| `审核_审核意见` | 写入③AI审核·审核意见 |
| `审核_关键实体抽取` | 写入③AI审核·关键实体抽取 |
| `审核_高风险词命中` | 写入③AI审核·高风险词命中 |
| `审核_平台规则预检` | 写入③AI审核·平台规则预检 |
| `审核_备案核查结果` | 写入③AI审核·备案核查结果 |
| `审核_推荐违规类型` | 多选数组；每个值必须已配置为飞书选项 |
| `审核_推荐风险等级` | 写入③AI审核·推荐风险等级 |
| `audit_time` | 毫秒时间戳，同时写入②、③段审核时间 |
| `matched_rules` | 格式化为文本，附加到审核意见末尾 |
| `routing` | 转换为⑤流转·当前状态 |

### 6.1 `routing` 状态映射

| 规则引擎返回 | 飞书状态 | 后续动作 |
| --- | --- | --- |
| `运营` | 待运营修改 | 推送运营修改卡片 |
| `运营补资料` | 待运营修改 | MVP 暂与运营路由相同 |
| `法务` | 待法务复核 | 通知法务 |
| 错误、超时或网络异常 | 运营起草 | 不写审核字段，推送失败卡片 |

当前联调记录显示，规则引擎已有规则默认路由均偏向法务，`routing=运营` 尚需配置可运营处理的规则后再补测。

### 6.2 违规类型枚举

飞书侧已补充规则引擎当前需要的选项。接口必须返回字符串数组，不能返回逗号拼接字符串。

当前规则引擎稳定输出范围包括：

- 绝对化用语；
- 虚假宣传；
- 涉医疗宣传；
- 价格促销误导；
- 平台准入/资质不符；
- 广告代言不合规；
- 广告可识别性不足；
- 引证内容不规范；
- 用户评价/种草误导；
- 未成年人保护；
- 其他。

飞书展示枚举与规则引擎内部维度后续应通过映射表解耦，不应为适配飞书而直接改写规则库维度。

## 7. 两类失败不能混在一起

### 7.1 `/audit` 失败

这是主审核链路失败：

- 飞书状态回退到“运营起草”；
- 不写入审核结果；
- 运营收到失败卡片；
- 允许重新点击触发。

### 7.2 `/cases/retrieve` 失败

这是相关案例辅助展示失败：

- 案例库返回 HTTP `503`、`code=-1` 和稳定的 `data.cases=[]`；
- 法务工作台记录异常后对前端降级为 `{"cases": []}` 或等价空结果；
- 页面展示“暂无相关案例”；
- 不修改飞书状态；
- 不影响 `/audit` 已生成的审核结果；
- 工作台后端总超时 8 秒，案例库建议 5 秒内返回。

## 8. 安全要求

1. API Key 只能通过安全渠道和部署环境变量提供；
2. 不得把 Key 写入 Word、Markdown、代码、Git 或完整请求日志；
3. 队友提供的 Word 文件中出现了明文 Key，该 Key 应立即轮换；
4. 新 Key 不在本确认稿中记录；
5. 所有响应返回 `X-Request-ID`；日志只记录请求 ID、耗时、状态码和索引版本，
   不记录物料正文或 API Key；
6. 候选案例不得在生产接口中静默返回。

## 10. 首轮联调验收

### 10.1 `/cases/retrieve`

- 请求字段类型和缺省值符合本稿；
- `top_k` 最大为 5；
- 同一案例不重复展示；
- BM25 分数不显示为百分比；
- 空生产索引返回 `cases=[]`；
- 生产接口不返回候选案例；
- 每条生产案例都有 `source_url` 和 `raw_text_path`；
- 响应包含 `X-Request-ID` 和 `retrieval_meta.index_version`；
- 5 秒内返回，8 秒时由工作台降级为空态。

### 10.2 `/audit`

- `code=0` 时飞书能读取全部中文 key；
- `审核_推荐违规类型` 是数组；
- `audit_time` 是毫秒时间戳；
- `routing=法务` 正确进入“待法务复核”；
- `routing=运营` 待规则配置后补测；
- 缺少 `content`、超时和网络异常均回退“运营起草”；
- 失败时不写入 ②、③段字段；
- 重复点击会被“AI预审中”状态拦截。
